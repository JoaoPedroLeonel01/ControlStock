# ControlStock - E-commerce Inventory Management System

ControlStock is an inventory management backend system designed specifically for apparel (clothing) e-commerce businesses. It provides transactional inventory control, clothing variation matrices (Size/Color/SKU), stock reservation workflows, and financial valuation.

Designed with a dual purpose:
1. **Software Engineering Showcase:** Clean architecture, strict domain modeling, ACID transactions with concurrency locks, automated tests, and CI/CD pipelines.
2. **Production-Ready Foundation:** Practical, battle-tested domain logic tailored for clothing retail operations.

## Key Features (MVP)

- **Clothing Matrix Catalog:** Parent products with variant combinations (reusable size grids with letters or numbers, Colors/Prints, per-product price tiers with price history, and auto-generated SKUs).
- **Three-Tier Stock Levels:** Real-time tracking of `Physical`, `Reserved`, and `Available` (`Physical - Reserved`) quantities.
- **Stock Reservation Engine:** 10-minute temporary reservation window for PIX checkout, with instantaneous settlement for credit/debit cards.
- **Zero-Negative Guarantee:** Database-level check constraints preventing negative stock quantities under any circumstance.
- **Immutable Inventory Ledger:** Audit trail tracking every inbound batch, outbound order, customer return with mandatory reason, and physical adjustment.
- **Reporting & Alerts:** Low-stock threshold alerts, valuation reports (total invested cost vs. potential retail revenue), and category/status filtering.

## Local Development

```bash
# 1. Environment variables (DATABASE_URL is required)
cp .env.example .env

# 2. Python dependencies (runtime + dev tools: pytest, ruff, httpx)
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt

# 3. Start PostgreSQL 16
docker compose up -d postgres

# 4. Apply database migrations
alembic upgrade head

# 5. Run the API
uvicorn src.control_stock.main:app --reload
```

### Database Migrations (Alembic)

Migration scripts live in `migrations/versions/`. New revisions are automatically
linted and formatted by Ruff (post-write hooks in `alembic.ini`).

```bash
alembic revision --autogenerate -m "create products table"  # generate from models
alembic upgrade head        # apply all pending migrations
alembic downgrade -1        # revert the last migration
alembic check               # fail if models and migrations are out of sync
```

> Always review autogenerated migrations before committing. New models must be
> imported in `src/control_stock/models.py` (the model registry loaded by
> `migrations/env.py`) to be detected by autogenerate.

### Quality Checks

```bash
ruff check . && ruff format --check .
pytest --cov                # fails below 80% coverage
```

### Tests

- `tests/unit/` — no database needed.
- `tests/integration/` — run against a real PostgreSQL 16: the database rules
  (stock triggers, CHECK constraints, immutable ledger) and concurrent
  reservations of the last unit.

Integration tests use their **own** database, set in `TEST_DATABASE_URL` (read
from the shell, not from `.env`). Its name must end in `_test`; it is created
automatically and its schema is rebuilt with `alembic upgrade head` on every run,
so never point it at a database you care about. Use the same server and
credentials as `DATABASE_URL`:

```bash
export TEST_DATABASE_URL=postgresql+psycopg://control_stock_user:control_stock_pass@localhost:5432/control_stock_test
pytest
```

Without `TEST_DATABASE_URL` the integration tests are skipped. In CI it is
required: the run aborts if it is missing.

## Deployment (Render + Neon)

The API runs on [Render](https://render.com) (native Python runtime, free plan) and the database on
[Neon](https://neon.com) (PostgreSQL 16, free plan). This repository is a prototype:
all data is fictitious.

1. **Database:** create a Neon project (PostgreSQL 16, region close to the Render
   service) and copy the **direct** connection string (host without `-pooler`).
   Neon's pooler (PgBouncer, transaction mode) is not suitable for migrations.
2. **Configuration:** in the Render service, set the environment variable
   `DATABASE_URL` to that connection string. Never commit it. `postgresql://` is
   converted to the psycopg driver automatically and `?sslmode=require` is kept.
3. **Deploy:** set the Render **Start Command** to

   ```bash
   alembic upgrade head && uvicorn src.control_stock.main:app --host 0.0.0.0 --port $PORT
   ```

   (Render's free plan has no Pre-Deploy Command). If a migration fails, the deploy
   fails, the previous version stays live and the error appears in the Render logs;
   the database is left unchanged because migrations run in a single transaction.
   The Docker image's `CMD` does the same when the app runs as a container.

> Free-plan behavior: the Render service sleeps when idle and the Neon compute
> suspends after 5 minutes without queries, so the first request after a pause is
> slower.
